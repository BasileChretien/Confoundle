# Confoundle

Mobile-first, open-source PWA that teaches people to spot flaws in causal/statistical reasoning by fooling them first, then revealing the trick. Atomic experience = one puzzle in four beats: **setup → commit → reveal → lesson**, ending in a shareable card. See [`PROJECT_PLAN.md`](./PROJECT_PLAN.md) for full product context; this repo is the **Phase 0 prototype** (one seed puzzle, generic engine).

## Commands

- `pnpm dev`: dev server (mobile-first; test at a phone-sized viewport)
- `pnpm build`: `tsc` type-check + `vite build` (emits PWA assets)
- `pnpm preview`: serve the production build
- `pnpm test`: Vitest (includes the seed-data paradox proof)
- `pnpm gen:icons`: regenerate PWA PNG icons from the brand motif

pnpm is provisioned via Corepack (`packageManager` is pinned). If `pnpm` isn't on PATH, use `corepack pnpm <cmd>`.

## Architecture

- `src/puzzles/`: the **contract**: `schema.ts` (single zod source of truth → inferred `Puzzle` type), `data/*.ts` (puzzle content), `index.ts` (registry; validates every puzzle at load).
- `src/engine/`: renders **any** puzzle from its data. Beats in `PuzzleFlow.tsx`; views in `SetupView`/`CommitView`/`RevealView`/`LessonView`/`share/ShareCard`. Generic chart via `charts/DataViewRenderer.tsx` → `RateChart.tsx`. **Pure derivation** (aggregate/stratified rates, reused by future Remotion templates) in `charts/rates.ts`.
- `src/app/`: PWA shell (`App.tsx`, `main.tsx`), `i18n.tsx`, `session.ts` (localStorage), `analytics.ts` (the funnel counter, into `event_tally`), `auth.tsx` + `AccountPanel.tsx` (optional sign-in).
- `src/srs/`: spaced repetition, scheduled per **skill** not per item. `schedule.ts` (pure stage ladder), `select.ts` (draws a fresh scenario each review), `store.ts` (the `ProgressStore` interface + localStorage), `remoteStore.ts` (the account-backed one + `syncStores`). Wired into the app through `src/app/reviews.ts` (enrol on learning, build/grade/persist a session) and `src/engine/ReviewView.tsx` (the review UI). A puzzle's `PuzzleFlow` enrols its skill at the lesson beat; `App.tsx` surfaces "Reviews due" and opens a session; a finished session syncs via `auth.syncProgress`.
- `src/server/` + `functions/api/**`: the account backend. All logic lives in `src/server/` so `tsc` and Vitest cover it; the files under `functions/` are thin adapters. `migrations/*.sql` is the D1 schema, and the tests run against those exact files through `node:sqlite` (a new migration must be added to the list in `src/server/testing/schema.ts`). See [`docs/accounts.md`](./docs/accounts.md).
- `worker/reminders.ts` + `wrangler.reminders.toml`: the **scheduled** half of the backend, deployed on its own (`pnpm deploy:reminders`) because **Pages Functions cannot carry a cron trigger**. It binds the same D1 and keeps its own copy of `SESSION_SECRET`, which must match the Pages one or every unsubscribe link it mints will look fine and silently fail to verify. Logic in `src/server/reminders.ts`, wording in `reminderEmail.ts` (its own ten-locale table, because importing `translations/all.ts` would blow the Worker's 1 MiB budget to render seven lines).
- `src/engine/games/overkill/`: the deterministic simulation behind **Overkill**, a browser arcade game where the damage meter is accurate and misleading and the death screen re-runs your own run without one weapon. Not wired to any UI yet. `rng.ts` (named streams + `foldSpawn`), `content.ts` (the tuning table), `sim.ts` (the tick loop), `replay.ts` (log, replay, paired counterfactual study), `policies.ts` (scripted players, for the headless balance tests). **The contract is reproducibility**: fixed timestep, no clock, no `Math.random`, no trigonometry (`Math.cos` is implementation-defined, so spawn directions come from rejection sampling and `Math.sqrt`, which is not). A source scan in `sim.test.ts` enforces all four and self-tests its own matcher. Four things cost real time to find. **A counterfactual must replay a LOG, never re-run a policy**: a reactive controller sees different enemies when a weapon is off, walks somewhere else, and moves every later spawn with it, so the arms stop being the same world; a test asserts that hazard is real rather than theoretical. **Spawn draws happen before the enemy cap is consulted**, or a run going badly consumes the stream at a different rate and every counterfactual silently compares two different games. **The arms are paired**, all measured on the same seeds including the arm with nothing removed, because the unpaired reading adds the player's own luck to every weapon identically: measured here at 5 to 140 seconds depending on the seed, which is larger than the smallest real effect the screen means to report. **A counterfactual cannot outlive its log**, so runs still alive at the end are marked `censored` and `summarise` refuses to pass off a censored median as a number. The tuning in `content.ts` is provisional and its job is to keep two properties alive: ice posts ~0% of the meter and is worth tens of seconds, and no weapon is generally good (which is what `armour` is for). Note the forward spawn bias: without it a fleeing player outruns everything, any slow wins the game on its own, and runs never end.

## Conventions (project-specific)

- **Adding a puzzle = one new data file** in `src/puzzles/data/` + a line in `index.ts`. Zero engine changes. A genuinely new data shape adds a `PuzzleData` union member in `schema.ts` and a branch in `DataViewRenderer.tsx`.
- **Build as many puzzles as the deck needs, without asking first.** Standing authorisation: there is no cap on how many puzzles ship in a session or a PR, and no need to check in before starting the next one. Work the queue in [`docs/lesson-backlog.md`](./docs/lesson-backlog.md) and keep going. The only limit is the one below, and it is not negotiable: **a puzzle ships when its numbers have been read at source and reconciled, and not before.** If a source cannot be reached, or its table does not print counts, or the figures do not reconcile, then the honest output is a backlog entry recording exactly that, and the next puzzle instead. Volume never buys a shortcut past provenance, and a session that ships one verified puzzle and three sourcing notes has done better work than one that ships four puzzles built on abstracts. One shippable unit per branch still applies, so several puzzles in a session means several PRs.
- **Build a new shape whenever the lesson needs one. Never bend a lesson to fit an existing shape.** The whole design rests on setup and reveal being two *views of the same data*, so if a bias cannot be told that way with the shapes on hand, the shape is what is missing, not the puzzle. Lead-time bias needed `timeline` because the claim was "the clock started earlier"; relative-versus-absolute risk needed `risk` because one bar chart cannot be both a proportion of the control risk and a proportion of everybody. A forced fit produces a reveal that just restates the setup, which is worse than the extra file. Adding a shape is: a union member in `schema.ts`, a pure derivation module in `engine/charts/` with a test, a renderer, a `DataViewRenderer` case plus `scopeLabel` entries for the new `DataView` kinds, a `full` prop if the shape draws a slice (the next bullet), a glyph in `share/ShareCard.tsx`, and **an `aria-label` written as one authored sentence with `{slot}` placeholders, never assembled by concatenation**. Existing puzzles stay untouched. Extending an *existing* shape follows the same spirit: add optional fields (never `.default()`, which the inferred type makes required and forces edits to every existing puzzle).
- **A renderer handed a slice takes `full` as well, and colours from that.** `restrict*` filters the very list the renderer then maps over, so that list's indices describe the BEAT and not the puzzle. Colour by them and an item drawn alone at the setup takes slot 0, then moves to its real slot when the reveal brings the others in, handing slot 0 to whichever item arrives first: a reader tracking a colour across the two beats is tracking two different things, which is the exact opposite of the promise the two beats make. `reporting-rate-violent-crime` shipped that way, its police line teal on its own and rust at the reveal, and nothing failed anywhere, because the legend recoloured in step and the figure stayed internally consistent while telling the reader the wrong story. So a slice-drawing renderer takes the unrestricted data as a second prop and resolves colour through `declaredColors` in `engine/charts/palette.ts`, or `declaredSlot` where a shape spends more than one palette entry per item, as `salience` does. Two things make this stick rather than needing to be remembered: the prop is required, so omitting it is a `tsc` error, and `declaredColors.test.ts` reads the list of slice-drawing renderers OFF `DataViewRenderer` instead of hard-coding it, so a shape built later is covered without its author knowing the check exists. What that scan forbids is a palette slot read out of a list, never a fixed one: `colorFor(0)` for the single line a shape draws, or `colorFor(past ? 1 : 0)` for the two sides of a threshold, are facts about the thing rather than positions in a list, and stay fine.
- **Never mark a well-reasoning player wrong in order to land a surprise.** Settled 2026-08-03, and it outranks the pull of a good reveal. The deck fools people by showing them data whose obvious reading is wrong, not by asking for something the setup does not license and then scoring them down for a reasonable answer. The operational test: work out what the skill actually licenses, which is usually a *direction* and only rarely a *magnitude*, then check that no two answer bands share that direction. If two do, one of two things must happen before the puzzle ships. Either put the discriminator in the framing, the way `statistical-power` states that the question is about size and pins it with a test comment, or make "There is no way to tell" the correct answer and let the reveal carry the surprise. The surprise lives in the reveal; the commit beat must be answerable. See [`docs/hedge-audit.md`](./docs/hedge-audit.md) for the three failure modes this catches, including the nastiest one, where the distractor is also right and nothing in the answer key looks wrong. **The rule governs the Trap Hunt bank exactly as it governs the four bands, and the bank is where it actually keeps breaking**: on 2026-08-12 it was violated six times across four cards, every one caught in review, because the bands get audited carefully and then fourteen items get written in one pass without the same check ever being run over them. `src/puzzles/hedgeTells.test.ts` now catches the part a machine can catch: a list of phrases that have really caused this, refused in any item tagged to a different skill. It reads the SCENARIO and not only the verdict, because the sixth defect was a single scene-setting adjective, "in a single-arm trial", which handed the player a second correct critique. It is a list of known tells rather than a proof, and it is meant to grow: when review finds a new one, add it there.
- **A toy that scores nothing goes after the reveal, and only where it has something to show.** `engine/charts/mixer.ts` + `MixerView.tsx` is the first: the reader drags how the cases were split and watches the aggregate winner swap while both within-group rates sit exactly where the source table put them. Five rules make it honest rather than a magic trick, and four of them exist because review found the opposite shipped. The within-group rates are the measured ones and **never move**, which is the whole claim. It is offered only where a **reversal** is reachable, which is strictly stronger than a crossing: `spectrum-bias` crosses and is still refused, because neither group leads in both strata, so the caption could never fire; `written-in-the-stars` never crosses at all. An earlier version of this bullet said both never crossed, which was false for one of them and would have invited relaxing the check. The caption asserting the reversal is a **claim**, so `reversedAt` is a pure function with its own test, and at the opening mix it must stay off screen. That opening mix is **not the midpoint**, because at the midpoint `kidney-stones` prints its own two headline numbers attached to the opposite arms, and a reader who just chose between them would meet them swapped. And **nothing in the chrome may know what the puzzle is about**: it said "treatments", "success rates" and "the hard cases" until review pointed out that all three are facts about one puzzle written into the engine, and that a table whose strata are authored in the other order gets a silently inverted slider with nothing checking. The slider names the stratum it moves by that stratum's own label. Placement matters for one more reason: nothing is graded there, so the hedge rule has no purchase and the toy can be as playful as it likes.
- **The second toy confirmed the pattern, and the refusal is the part that generalises.** `engine/charts/screen.ts` + `ScreenView.tsx` does for base rates what the mixer does for Simpson's paradox: the test's two characteristics are held exactly as measured, the reader drags how common the condition is among the people tested, and the worth of a positive swings from 2% to 95% on the same test. Everything the mixer rule says applies unchanged, and three things are new. **Where the mixer could refuse on arithmetic, this one cannot.** `courtroom-odds` is the same `frequencies` shape, its verdict flips, and every structural check passes, so with the flag set it WOULD be offered; dragging it is still nonsense, because one crime happened and "how many couples did it" is not a dial. So the puzzle declares it, with an optional opt-in `baseRateCanVary`, and a puzzle that says nothing gets no toy. **When a toy's honesty depends on a fact about the world rather than about the numbers, the data has to carry that fact.** Second, this shape reproduces the puzzle's own published counts at the authored base rate, which is its analogue of the mixer's fixed stratum rates. Third, and this is the one that cost the most: **a claim withheld at an exact tie must also be withheld across the band that DISPLAYS as a tie**, because the share is drawn to the nearest whole percent and "fewer than half" printed beside a figure reading 50% is the figure contradicting itself.
- **The third toy: multiplicity, and the lesson is that whether subgroups mislead is LUCK.** `engine/charts/subgroups.ts` + `SlicerView.tsx` holds ISIS-2's pooled result still, lets the reader cut its patients into up to 24 subgroups, and lets them RE-DEAL. The patients are dealt, not simulated: every subgroup is the trial's own people carrying the outcomes they really had, so counts always add back to the pooled totals and one slice is the trial itself. The re-deal button is the important control, and it exists because of a mistake worth keeping in view. The first version had one deal per slice count and argued from it: twelve ways produces no contradiction, therefore groups of seven hundred are too big to reverse, therefore the cap must exceed twelve. **Measured over two thousand deals, 43.8% give no contradiction at twelve and 56.2% give at least one, mean 0.70.** The claim was a property of one seed. It was also making the page argue with itself, since the puzzle is about a trial that WAS cut twelve ways and DID find a subgroup pointing the other way. So no single deal carries a claim now, and every test asserts across deals: at twelve, both outcomes are ordinary; averaged over deals, more cuts buy more contradictions. **When a figure draws one sample, ask what fraction of samples would have supported the sentence beside it.**
- **A number the translator cannot see must never stand where something has to agree with it.** Second shape to need this rule, so it is now a rule. The slicer's verdict read "{contrary} of the {n} subgroups now point away from {winner}", which is broken in six languages at once: English, French, Spanish, Portuguese and Hindi all need a singular verb at one, Russian needs a different noun form at two, three and four, and Arabic needs the dual at two. `{winner}` was worse, arriving as a bare nominative that Russian cannot decline after a preposition and French cannot elide before a vowel. No amount of translation fixes any of it, because the translator never sees the number or the noun. The fix is structural: the sentence carries no count at all ("Some subgroups now disagree with the trial"), and the counts move to labelled rows where a numeral is followed by "of" and by nothing that must agree with it. Check this by RENDERING the assembled sentences and reading them; the dictionary parity test cannot see grammar, and `chartsLocalized` does not reach a component `DataViewRenderer` never mounts.
- **A guard read by both the code and its test cannot be tested by that test.** Three toys made `hasToy` worth extracting so `LessonView` and `toyBadge.test.ts` could not disagree about which puzzles advertise one. That is right, and it silently made the badge test unable to catch `hasToy` being wrong: deleting a toy from the disjunction moved both sides of its assertion and left all 74 cases green with a shipped toy losing its badge. The fix is a second test that names the predicates one by one, plus a count that fails on the next toy so somebody has to look. The general shape is worth remembering, because the instinct that produces it is a good one: **when you extract a shared definition to stop two places drifting, check what was independently verifying it before, and rebuild that somewhere else.**
- **A guard that another guard already covers is not tested by a test that names it.** Three separate times on these two toys, a check was written, a test was written asserting the behaviour it protects, the test passed, and deleting the check changed nothing, because something else refused the same input first. The worst case was not the dead code but the STORY: six places in the repo said `courtroom-odds` passes every structural check and is stopped only by its opt-in flag, while in fact `flips` was sampling one person in from each end, hitting that puzzle's 1-against-1 tie, and refusing it on arithmetic. The flag was decorative and the test asserting it was a tautology that passed with the whole mechanism deleted. Two rules follow. **Take the ends of a range at the ends** unless there is a reason written down, since stepping inside is how a degenerate sample becomes an accidental refusal. And when a guard really is redundant, **say so where it lives and stop the test claiming otherwise**: `canScreen`'s population and sensitivity checks are kept for legibility with a comment saying `flips` already covers them, which is honest, where a test named "refuses a test that catches nobody" implying it isolates that line is not.
- **A comparison in the engine reads `higherIsBetter` or it is wrong half the time.** The mixer compared with `>` throughout and every test passed, because the one puzzle it accepted counts successes. On a mortality table the same code names the arm that kills more people as the winner, and prints it, in ten languages, on a translated sentence: the exact inverse of the paradox the figure exists to demonstrate. It was unreachable in the deck only by coincidence, since `written-in-the-stars` is already `higherIsBetter: false` and already passes the structural check, refused for an unrelated reason. The generalisable part is that **a shape tested against one puzzle is tested against that puzzle's conventions**, so any new derivation that ranks, orders, or picks a winner needs a synthetic counter-example with the flag flipped, in the same PR. `mixer.test.ts`'s "when lower is better" block is the pattern: build the table, assert the reading, then flip the flag alone and assert the reading inverts, which is what proves the flag is read rather than defaulted.
- **A chart's `aria-label` is an authored sentence, not a template literal.** `` `${t(data.cause)} and ${t(data.effect)} rise together` `` is one English sentence with its holes where English puts them: no translator ever sees it, so it announced English in all ten locales while the figure beside it was fully translated. Write the whole sentence as `t({ en: "{cause} and {effect} rise together" })` and drop the values in with `fillSlots` from `engine/charts/announce.ts`, so clause order is the translator's to choose. Japanese counts the whole before the part ("3 of 40" is 40人中3人, operands reversed) and marks a time with a particle after it rather than a word before it, so there is often no English preposition to translate and nowhere to stand one. Two rules follow. **A conditional tail is a second whole sentence, never a fragment appended**: ", highest" and ", crossing no difference" have no sentence to sit in, and a translator handed one has to guess what it will be glued to. **Slots that must stay adjacent are one slot**: a duration and its unit go in together, because splitting them only lets a translation separate them. Slot names are lowercase letters only, since that is what the retention check in `translations/inlineChrome.test.ts` matches. `chartsLocalized.test.ts` enforces all of this by *rendering* every puzzle in six non-Latin locales, which is the only thing that can see a string that was never wrapped; its `ANNOUNCED_IN_ENGLISH` list is at zero and may only shrink.
- **Numbers are authored once** as raw `observations`; all rates are derived. Never hardcode a percentage that could contradict the counts.
- **Every numeral a chart draws follows the reader's locale, and a figure is converted whole or not at all.** Build an `Intl.NumberFormat` from `useLocale()` (or take the locale as an argument, in a pure module any surface can call), and never reach for `toLocaleString`: a literal locale like `toLocaleString("en-US")` pins English grouping in all ten languages, and an ARGUMENT-LESS `toLocaleString()` or `new Intl.NumberFormat()` is worse, because it looks like the fix and silently follows the JavaScript runtime's default, which in a browser is the browser's language rather than the one the reader picked in the app. Two of these even carried a comment reading "locale-aware grouping", true of the mechanism and false of the locale. Nothing caught any of it: `chartsLocalized.test.ts` matches runs of two or more Latin *letters* and never looks at digits, so a chart drawing `40,320` at a French reader who writes `40 320` sweeps up perfectly clean. `src/localeNumerals.test.ts` is the source scan that does catch it, built like `declaredColors.test.ts` and blind in the same way. **It scans engine, app, srs, server and puzzles, and it did not always**: it globbed one directory from inside `engine/charts/` while reading as though it covered the engine, so every top-level view was outside it and `TrapHuntView` and `CalibrationRunView` both formatted counts for the reader with nothing looking. That is the `scopeLabels` hole again, a guard whose name promises more than its glob delivers, so when you add a scan, assert the directories it matched and not only the total. which is why the second half of the rule matters more than the first: **converting some numerals in a figure and not others is worse than converting none**, and no scan can see it. `EcologicalView` drew `১,৩০৪ / ১৩,২১৭ (9.9%)` inside a single span, and `UnseenView` grouped its counts through `Intl` while the percentages summarising them came from `toFixed`. So when you touch a figure, convert every number in it, including axis ends and the `aria-label`'s copy of the same value. `toFixed` is the remaining hole: it localises nothing, twenty-odd files still use it, and they are at least uniformly unlocalised rather than half. When one is converted, add it to that scan.
- **Every user-facing string is locale-keyed** (`{ en: … }`). Use `useT()` / `translate()` from `app/i18n`; never inline a bare display string that a puzzle should own.
- **Translations are enforced, not remembered.** `src/app/translations/coverage.test.ts` fails if any authored English string is missing from any of the nine dictionaries, or if the dictionaries drift out of key parity. Dictionaries are keyed by the exact English source text, so a key that differs by one character fails silently at runtime and falls back to English forever: always copy keys programmatically, never retype them. To get the worklist as JSON (the failure message has the same content, but JSON lets a translation pass generate entries by script), drop a throwaway `src/app/translations/_worklist.test.ts` that imports `DICTIONARIES`, `puzzles`, `TEST_ITEMS` and `TAGS`, walks them for every object with a string `en`, and writes `{ locale: missingStrings[] }` via `await import("node:fs")`. Run it, then delete it. It cannot live in the repo permanently because the project carries no `@types/node`. Note that engine chrome (the `scopeLabel` strings, share-card text) is *not* reachable by that walk, so new view kinds need their scope labels translated by hand.
- **A component whose failure mode is a BLANK SCREEN needs a DOM, and gets one per file.** The suite is `environment: "node"` on purpose, because the engine is pure derivation, and every component test goes through `renderToStaticMarkup`, which runs no effects and no error boundaries. That is fine until the thing under test IS an effect. `LocaleProvider` renders `null` until its dictionary lands, so the `ready` gate, the document's `lang` and `dir`, and the stored locale choice were all invisible to 166 test files; two reviews had to stand up a React root by hand to answer questions about them. `src/app/localeProviderPaint.test.ts` opts in with a `// @vitest-environment happy-dom` docblock, which costs about half a second and leaves the other files untouched. **Adding the environment is the easy half: spend it on the effects.** The first version of that file added a DOM and covered only the paint gate, and review then pinned `lang` to "en", `dir` to "ltr", deleted the stored choice, deleted the `LOCALE_CODES` check and deleted the stale-load race guard, ALL AT ONCE, and the full suite stayed green. Note also that `happy-dom` pulls `@types/node` in transitively, so the project's "no `@types/node`" property now holds only because `tsconfig.json` pins `"types"`; widening that list silently admits Node globals. Four traps if you write another such test. `createElement(type, props, ...children)` overwrites `props.children` from the variadic tail, so an explicit `undefined` there blanks the subtree and reads exactly like the gate being shut. A statically imported hook resolves to a DIFFERENT module instance than an `await import()` after `vi.resetModules()`, so it reads the context default and every state change silently does nothing while the tests pass. `act` flushes the commit and the passive effects together, so it cannot tell a one-commit render from a two-commit one: to assert what the reader's first frame contained, commit it with `flushSync` and look before the effects run. And a promise that settles in a MICROTASK lets React batch two `setState`s into one commit, so an intermediate state you mean to assert never gets painted; hold the promise open if the intermediate state is the point.
- **Rigor is existential.** Every puzzle's factual claim needs `provenance` (enforced by schema). Don't oversimplify, see [`CONTRIBUTING.md`](./CONTRIBUTING.md).
- **Respect `prefers-reduced-motion`** in any new animation (see `useReducedMotion` / `useCountUp`).
- **Accounts are optional and buy exactly one thing.** Signing in makes the SRS schedule follow you between devices. Nothing else syncs, nothing is gated on an account, and a build with no functions behind it hides the panel rather than showing something broken. There is no password column and no plan for one: both sign-in routes prove control of an email address, which is what makes linking them safe. Every field stored is listed in [`docs/data-inventory.md`](./docs/data-inventory.md), and the published policy is `public/privacy.html`. **Adding anything that holds personal data means adding its table to `PERSONAL_TABLES` in `src/server/accounts.ts`**, or erasure will silently leave it behind; the test in `accounts.test.ts` checks that list is complete. The funnel counter is no longer a stub: it writes the eight fixed step names to `event_tally` in this project's own D1, never to an analytics company, and its prop type is narrowed to the single column that table has so a call site cannot widen what is transmitted without `tsc` refusing. It obeys the same switch as the answer tally. Keep the answers, streaks and scores local, and keep anything that could identify a person out of all three: no session id, no clock time, no ordering, which is what lets `event_tally` and `answer_tally` stay out of `PERSONAL_TABLES`.
- **Every lesson is also a static page you can paste into an argument.** `pnpm build` prerenders `dist/l/<slug>/[<locale>/]` (160 pages) via the plugin in `vite.config.ts`, from `src/server/lessonPage.ts` and `prerender.ts`. It opens on the ANSWER, unlike the puzzle, because a debate link that tests the reader reads as a trap. Prerendered rather than served by a Pages Function because that version measured 910 KB gzipped against a 1 MiB Functions budget, almost all of it the nine dictionaries. Two traps if you touch this: the pages must stay out of the PWA precache (`globIgnores`) **and** out of its navigation fallback (`navigateFallbackDenylist`), or an installed app answers a shared link with the app shell. `vite.config.ts` is the one legitimate importer of `translations/all.ts`, since it is a build script rather than the app.
- **Chrome strings are translated too.** `src/app/ui.ts` (`UI`, `ACCOUNT`, `LESSON_SHARE`) carries all ten locales inline, enforced by `src/app/ui.test.ts`, and `src/server/lessonPageStrings.ts` (`LESSON_PAGE`) does the same for the prerendered lesson pages, enforced by `lessonPageStrings.test.ts`. This is separate from the dictionary coverage test, which only walks puzzles, test items and tags and therefore cannot see interface strings. The engine also writes chrome inline as `t({ en: "Next" })`, which resolves through the dictionaries and so needs a hand-added key in the "UI chrome" block at the top of all nine. That form is fine, but only because `src/app/translations/inlineChrome.test.ts` now scans the source for it (via `import.meta.glob(..., "?raw")`, since there is no `@types/node`) and fails if any locale lacks the key. Without that scan the string ships untranslated in nine languages with nothing failing anywhere, because a dictionary miss falls back to English by design: that is how every heading on 342 lesson pages, and the whole of `ReviewView`, stayed English. The scan strips comments before matching, so quoting the pattern in prose is safe. **A string that interpolates a value takes a `{slot}`, never a fragment plus a variable**: the skill name does not fall at the end of "Does this fall for {skill}?" in Japanese, Hindi or Arabic, and the question mark is not `?` in all of them. Slot retention is enforced by the same test.
- **A `t()` argument that is COMPUTED rather than written out is invisible to both translation guards, and that gap is where nine chart captions lived.** `t({ en: "Next" })` is caught by `inlineChrome.test.ts` because the scan reads the source for that literal shape. But `t({ en: scopeLabel(view.kind) })` and `t({ en: reactionFor(caught, confidence) })` pass a value computed at runtime, so the scan cannot match it, and the strings are engine chrome rather than puzzle content, so `coverage.test.ts` never walks them either. Two tests that each look like they cover this both structurally cannot. All 72 scope labels sat in that gap and nine of them were in no dictionary at all, including `"As one judge marked it"`, masked only because the single `raters` puzzle sets explicit captions on both views: the next `raters` puzzle would have shipped English to nine languages with a green suite. The fix is a test per computed-key site that resolves the values and checks them against `ALL_DICTIONARIES`, and the rule is that **the enumeration must be read off a runtime source, never hand-listed**: `charts/scopeLabels.test.ts` takes its kinds off `DataView.options`, the zod union, so a view kind added later is covered without its author knowing the test exists, exactly as `declaredColors.test.ts` reads its renderer list off `DataViewRenderer`. A hand-written list would have to be maintained by the person least likely to know it exists. `engine/scoring.test.ts` does the same for `reactionFor`. **Adding a function that returns bare English for a `t()` call site means adding its enumeration test in the same PR.** Beware also that a grep for a dictionary key can lie in the other direction: four of these labels are written as BARE IDENTIFIERS rather than quoted strings, so searching the source for `"Overall"` reported a gap that did not exist. Check membership against the imported object, never against the file text.
- **The planning docs are enforced too, for the same reason.** `docs/lesson-backlog.md` is the queue and `docs/exam-syllabus-audit.md` is the coverage record, and both silently rotted before: three shipped lessons still read "READY TO AUTHOR" or "LEAD", and statistical power sat at **gap** for weeks after it shipped. A stale planning doc is worse than none, because it makes somebody re-research finished work or believe in a hole that is closed. So each tracked row carries a machine-readable `<!-- skill: id -->` tag naming the `reasoningSkill` it ships under, and `src/puzzles/docsCoverage.test.ts` fails if a tagged skill is in the registry but its entry does not say SHIPPED, if an entry claims SHIPPED for a skill that does not exist, if a numbered backlog entry has no tag, or if an audit row says **gap** while tagged with a shipped skill (or says gap with no tag at all, since nothing could then check it). **Shipping a puzzle means updating its row in the same PR**; the suite will not let you forget. The one hole the test cannot see is shipping a backlogged lesson under a *different* skill id than its tag declares, so if the id changes, change it in both places.

- **The app shell has about 100 KiB of precache budget left, and that ceiling is doing useful work.** `pnpm build` reports `precache 10 entries`, essentially `index-*.js` plus the CSS and icons; the dictionaries are code-split and deliberately excluded (`globIgnores`), so the number is the shell alone. At 73 puzzles it measured **1,988,364 bytes, 94.8% of workbox's 2 MiB default**, and every puzzle adds to it. **The failure is loud, and was checked rather than assumed**: vite-plugin-pwa 1.3.0 throws `PLUGIN_ERROR` from `logWorkboxResult`, naming the file, its size and the config key, so the build stops. An earlier version of this bullet claimed the file was silently dropped and a whole guard plugin was written against that; forcing the case by lowering the limit proved the opposite, and both were deleted. **When it does hit, the answer is almost certainly NOT to raise `maximumFileSizeToCacheInBytes`.** The ceiling is the one signal that the install is getting heavy, and raising it trades a build error for a slower first visit on a phone, silently. Split the puzzle data out of the shell the way the dictionaries already are, and keep the budget.

## Stack

Vite + React + TypeScript · **Tailwind CSS v4** (CSS-first: the theme lives in the `@theme` block of `src/styles/index.css`, there is no `tailwind.config.ts` and no PostCSS config, and `@tailwindcss/vite` replaces both) · vite-plugin-pwa · zod v4 · motion (framer-motion) · html-to-image. **Node ≥ 22.13**, pinned in `.node-version`: the pinned pnpm uses `node:sqlite` internally, so an older Node fails at `pnpm install` with `ERR_UNKNOWN_BUILTIN_MODULE` before any project code runs. The server tests need the same builtin.

**Every build prints about 150 lines of "without a file extension" warning, and it is expected.** Vite 8.2 added a forward-compatibility notice listing config features unsupported by `configLoader: 'native'`, which it says will become the default in a future major. The build is unaffected today (the default is still `bundle`, and passing `--configLoader bundle` explicitly does not silence the notice, since it is about the future rather than the present). It is long because `vite.config.ts` imports the puzzle registry and `translations/all.ts` in order to prerender the lesson pages, so the notice walks that whole graph and names every extensionless import and the one directory-index import behind it. Two things follow. When that default does flip, the thing that breaks is the prerender, which is to say all 660 lesson pages, so this is worth acting on before it lands rather than after. And until then the notice buries the rest of the build output, which matters here more than usual: `vite.config.ts` explains at length that the contact-email guard FAILS rather than warns precisely because a warning scrolls past unread in a wall of asset sizes. Fixing it properly means adding file extensions to every import reachable from the config, which is around 150 sites across `src/puzzles/`, `src/app/translations/` and `src/server/`; `VITE_CONFIG_NATIVE_IGNORE_WARNING=true` only hides it.
