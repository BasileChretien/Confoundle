# Confoundle

Mobile-first, open-source PWA that teaches people to spot flaws in causal/statistical reasoning by fooling them first, then revealing the trick. Atomic experience = one puzzle in four beats: **setup → commit → reveal → lesson**, ending in a shareable card. See [`PROJECT_PLAN.md`](./PROJECT_PLAN.md) for full product context; this repo is the **Phase 0 prototype** (one seed puzzle, generic engine).

## Commands

- `pnpm dev`: dev server (mobile-first; test at a phone-sized viewport)
- `pnpm build`: `tsc` type-check + `vite build` (emits PWA assets)
- `pnpm preview`: serve the production build
- `pnpm test`: Vitest (includes the seed-data paradox proof)
- `pnpm gen:icons`: regenerate PWA PNG icons from the brand motif

pnpm is provisioned via Corepack (`packageManager` is pinned). If `pnpm` isn't on PATH, use `corepack pnpm <cmd>`.

## Architecture

- `src/puzzles/`: the **contract**: `schema.ts` (single zod source of truth → inferred `Puzzle` type), `data/*.ts` (puzzle content), `index.ts` (registry; validates every puzzle at load).
- `src/engine/`: renders **any** puzzle from its data. Beats in `PuzzleFlow.tsx`; views in `SetupView`/`CommitView`/`RevealView`/`LessonView`/`share/ShareCard`. Generic chart via `charts/DataViewRenderer.tsx` → `RateChart.tsx`. **Pure derivation** (aggregate/stratified rates, reused by future Remotion templates) in `charts/rates.ts`.
- `src/app/`: PWA shell (`App.tsx`, `main.tsx`), `i18n.tsx`, `session.ts` (localStorage), `analytics.ts` (no-op stub), `auth.tsx` + `AccountPanel.tsx` (optional sign-in).
- `src/srs/`: spaced repetition, scheduled per **skill** not per item. `schedule.ts` (pure stage ladder), `select.ts` (draws a fresh scenario each review), `store.ts` (the `ProgressStore` interface + localStorage), `remoteStore.ts` (the account-backed one + `syncStores`). Wired into the app through `src/app/reviews.ts` (enrol on learning, build/grade/persist a session) and `src/engine/ReviewView.tsx` (the review UI). A puzzle's `PuzzleFlow` enrols its skill at the lesson beat; `App.tsx` surfaces "Reviews due" and opens a session; a finished session syncs via `auth.syncProgress`.
- `src/server/` + `functions/api/**`: the account backend. All logic lives in `src/server/` so `tsc` and Vitest cover it; the files under `functions/` are thin adapters. `migrations/*.sql` is the D1 schema, and the tests run against those exact files through `node:sqlite` (a new migration must be added to the list in `src/server/testing/schema.ts`). See [`docs/accounts.md`](./docs/accounts.md).
- `worker/reminders.ts` + `wrangler.reminders.toml`: the **scheduled** half of the backend, deployed on its own (`pnpm deploy:reminders`) because **Pages Functions cannot carry a cron trigger**. It binds the same D1 and keeps its own copy of `SESSION_SECRET`, which must match the Pages one or every unsubscribe link it mints will look fine and silently fail to verify. Logic in `src/server/reminders.ts`, wording in `reminderEmail.ts` (its own ten-locale table, because importing `translations/all.ts` would blow the Worker's 1 MiB budget to render seven lines).

## Conventions (project-specific)

- **Adding a puzzle = one new data file** in `src/puzzles/data/` + a line in `index.ts`. Zero engine changes. A genuinely new data shape adds a `PuzzleData` union member in `schema.ts` and a branch in `DataViewRenderer.tsx`.
- **Build as many puzzles as the deck needs, without asking first.** Standing authorisation: there is no cap on how many puzzles ship in a session or a PR, and no need to check in before starting the next one. Work the queue in [`docs/lesson-backlog.md`](./docs/lesson-backlog.md) and keep going. The only limit is the one below, and it is not negotiable: **a puzzle ships when its numbers have been read at source and reconciled, and not before.** If a source cannot be reached, or its table does not print counts, or the figures do not reconcile, then the honest output is a backlog entry recording exactly that, and the next puzzle instead. Volume never buys a shortcut past provenance, and a session that ships one verified puzzle and three sourcing notes has done better work than one that ships four puzzles built on abstracts. One shippable unit per branch still applies, so several puzzles in a session means several PRs.
- **Build a new shape whenever the lesson needs one. Never bend a lesson to fit an existing shape.** The whole design rests on setup and reveal being two *views of the same data*, so if a bias cannot be told that way with the shapes on hand, the shape is what is missing, not the puzzle. Lead-time bias needed `timeline` because the claim was "the clock started earlier"; relative-versus-absolute risk needed `risk` because one bar chart cannot be both a proportion of the control risk and a proportion of everybody. A forced fit produces a reveal that just restates the setup, which is worse than the extra file. Adding a shape is: a union member in `schema.ts`, a pure derivation module in `engine/charts/` with a test, a renderer, a `DataViewRenderer` case plus `scopeLabel` entries for the new `DataView` kinds, and a glyph in `share/ShareCard.tsx`. Existing puzzles stay untouched. Extending an *existing* shape follows the same spirit: add optional fields (never `.default()`, which the inferred type makes required and forces edits to every existing puzzle).
- **Never mark a well-reasoning player wrong in order to land a surprise.** Settled 2026-08-03, and it outranks the pull of a good reveal. The deck fools people by showing them data whose obvious reading is wrong, not by asking for something the setup does not license and then scoring them down for a reasonable answer. The operational test: work out what the skill actually licenses, which is usually a *direction* and only rarely a *magnitude*, then check that no two answer bands share that direction. If two do, one of two things must happen before the puzzle ships. Either put the discriminator in the framing, the way `statistical-power` states that the question is about size and pins it with a test comment, or make "There is no way to tell" the correct answer and let the reveal carry the surprise. The surprise lives in the reveal; the commit beat must be answerable. See [`docs/hedge-audit.md`](./docs/hedge-audit.md) for the three failure modes this catches, including the nastiest one, where the distractor is also right and nothing in the answer key looks wrong.
- **Numbers are authored once** as raw `observations`; all rates are derived. Never hardcode a percentage that could contradict the counts.
- **Every user-facing string is locale-keyed** (`{ en: … }`). Use `useT()` / `translate()` from `app/i18n`; never inline a bare display string that a puzzle should own.
- **Translations are enforced, not remembered.** `src/app/translations/coverage.test.ts` fails if any authored English string is missing from any of the nine dictionaries, or if the dictionaries drift out of key parity. Dictionaries are keyed by the exact English source text, so a key that differs by one character fails silently at runtime and falls back to English forever: always copy keys programmatically, never retype them. To get the worklist as JSON (the failure message has the same content, but JSON lets a translation pass generate entries by script), drop a throwaway `src/app/translations/_worklist.test.ts` that imports `DICTIONARIES`, `puzzles`, `TEST_ITEMS` and `TAGS`, walks them for every object with a string `en`, and writes `{ locale: missingStrings[] }` via `await import("node:fs")`. Run it, then delete it. It cannot live in the repo permanently because the project carries no `@types/node`. Note that engine chrome (the `scopeLabel` strings, share-card text) is *not* reachable by that walk, so new view kinds need their scope labels translated by hand.
- **Rigor is existential.** Every puzzle's factual claim needs `provenance` (enforced by schema). Don't oversimplify, see [`CONTRIBUTING.md`](./CONTRIBUTING.md).
- **Respect `prefers-reduced-motion`** in any new animation (see `useReducedMotion` / `useCountUp`).
- **Accounts are optional and buy exactly one thing.** Signing in makes the SRS schedule follow you between devices. Nothing else syncs, nothing is gated on an account, and a build with no functions behind it hides the panel rather than showing something broken. There is no password column and no plan for one: both sign-in routes prove control of an email address, which is what makes linking them safe. Every field stored is listed in [`docs/data-inventory.md`](./docs/data-inventory.md), and the published policy is `public/privacy.html`. **Adding anything that holds personal data means adding its table to `PERSONAL_TABLES` in `src/server/accounts.ts`**, or erasure will silently leave it behind; the test in `accounts.test.ts` checks that list is complete. Analytics is still a no-op stub with fixed funnel event names; keep it that way, and keep the answers, streaks and scores local.
- **Every lesson is also a static page you can paste into an argument.** `pnpm build` prerenders `dist/l/<slug>/[<locale>/]` (160 pages) via the plugin in `vite.config.ts`, from `src/server/lessonPage.ts` and `prerender.ts`. It opens on the ANSWER, unlike the puzzle, because a debate link that tests the reader reads as a trap. Prerendered rather than served by a Pages Function because that version measured 910 KB gzipped against a 1 MiB Functions budget, almost all of it the nine dictionaries. Two traps if you touch this: the pages must stay out of the PWA precache (`globIgnores`) **and** out of its navigation fallback (`navigateFallbackDenylist`), or an installed app answers a shared link with the app shell. `vite.config.ts` is the one legitimate importer of `translations/all.ts`, since it is a build script rather than the app.
- **Chrome strings are translated too.** `src/app/ui.ts` (`UI`, `ACCOUNT`, `LESSON_SHARE`) carries all ten locales inline, enforced by `src/app/ui.test.ts`, and `src/server/lessonPageStrings.ts` (`LESSON_PAGE`) does the same for the prerendered lesson pages, enforced by `lessonPageStrings.test.ts`. This is separate from the dictionary coverage test, which only walks puzzles, test items and tags and therefore cannot see interface strings. The engine also writes chrome inline as `t({ en: "Next" })`, which resolves through the dictionaries and so needs a hand-added key in the "UI chrome" block at the top of all nine. That form is fine, but only because `src/app/translations/inlineChrome.test.ts` now scans the source for it (via `import.meta.glob(..., "?raw")`, since there is no `@types/node`) and fails if any locale lacks the key. Without that scan the string ships untranslated in nine languages with nothing failing anywhere, because a dictionary miss falls back to English by design: that is how every heading on 342 lesson pages, and the whole of `ReviewView`, stayed English. The scan strips comments before matching, so quoting the pattern in prose is safe. **A string that interpolates a value takes a `{slot}`, never a fragment plus a variable**: the skill name does not fall at the end of "Does this fall for {skill}?" in Japanese, Hindi or Arabic, and the question mark is not `?` in all of them. Slot retention is enforced by the same test.
- **The planning docs are enforced too, for the same reason.** `docs/lesson-backlog.md` is the queue and `docs/exam-syllabus-audit.md` is the coverage record, and both silently rotted before: three shipped lessons still read "READY TO AUTHOR" or "LEAD", and statistical power sat at **gap** for weeks after it shipped. A stale planning doc is worse than none, because it makes somebody re-research finished work or believe in a hole that is closed. So each tracked row carries a machine-readable `<!-- skill: id -->` tag naming the `reasoningSkill` it ships under, and `src/puzzles/docsCoverage.test.ts` fails if a tagged skill is in the registry but its entry does not say SHIPPED, if an entry claims SHIPPED for a skill that does not exist, if a numbered backlog entry has no tag, or if an audit row says **gap** while tagged with a shipped skill (or says gap with no tag at all, since nothing could then check it). **Shipping a puzzle means updating its row in the same PR**; the suite will not let you forget. The one hole the test cannot see is shipping a backlogged lesson under a *different* skill id than its tag declares, so if the id changes, change it in both places.

## Stack

Vite + React + TypeScript · **Tailwind CSS v4** (CSS-first: the theme lives in the `@theme` block of `src/styles/index.css`, there is no `tailwind.config.ts` and no PostCSS config, and `@tailwindcss/vite` replaces both) · vite-plugin-pwa · zod v4 · motion (framer-motion) · html-to-image. **Node ≥ 22.13**, pinned in `.node-version`: the pinned pnpm uses `node:sqlite` internally, so an older Node fails at `pnpm install` with `ERR_UNKNOWN_BUILTIN_MODULE` before any project code runs. The server tests need the same builtin.

**Every build prints about 150 lines of "without a file extension" warning, and it is expected.** Vite 8.2 added a forward-compatibility notice listing config features unsupported by `configLoader: 'native'`, which it says will become the default in a future major. The build is unaffected today (the default is still `bundle`, and passing `--configLoader bundle` explicitly does not silence the notice, since it is about the future rather than the present). It is long because `vite.config.ts` imports the puzzle registry and `translations/all.ts` in order to prerender the lesson pages, so the notice walks that whole graph and names every extensionless import and the one directory-index import behind it. Two things follow. When that default does flip, the thing that breaks is the prerender, which is to say all 660 lesson pages, so this is worth acting on before it lands rather than after. And until then the notice buries the rest of the build output, which matters here more than usual: `vite.config.ts` explains at length that the contact-email guard FAILS rather than warns precisely because a warning scrolls past unread in a wall of asset sizes. Fixing it properly means adding file extensions to every import reachable from the config, which is around 150 sites across `src/puzzles/`, `src/app/translations/` and `src/server/`; `VITE_CONFIG_NATIVE_IGNORE_WARNING=true` only hides it.
